\chap{Setup and Execution}
% ============================================================


\sect{Dependencies}

The project requires Python 3.10 or later. All dependencies are listed in \texttt{requirements.txt} and can be installed with:

\begin{minted}{bash}
pip install -r requirements.txt
\end{minted}

The key packages are:

\begin{itemize}
    \item \texttt{openai} --- LLM access for planning, code generation, response generation, and visualization code generation
    \item \texttt{langgraph} --- agent orchestration through directed stateful nodeexecution
    \item \texttt{langchain}-core --- LangGraph dependency
    \item \texttt{pandas} --- dataset loading and structured data analysis
    \item \texttt{plotly} --- visualization generation
    \item \texttt{fastapi} --- backend API
    \item \texttt{uvicorn} --- backend server
    \item \texttt{json} --- memory and artifact persistence
\end{itemize}

\sect{Configuration}

The agent authenticates with OpenAI using the environment variable \texttt{OPENAI\_API\_KEY}, which should be exported:

\begin{minted}{bash}
export OPENAI_API_KEY="sk-..."
\end{minted}

Optionally, turn off LLM caching:

\begin{minted}{bash}
export LLM\_CACHE=0
\end{minted}

This enables local caching of repeated LLM calls, significantly reducing cost and latency during development.

\sect{Stack Description}

The frontend communicates with the FastAPI server and provides:

\begin{itemize}
    \item Dataset selection
    \item Session management
    \item Chat history
    \item Visualization rendering
    \item Debugging views
\end{itemize}

The system is implemented as a LangGraph state machine composed of modular nodes:

\begin{multicols}{2}
    \texttt{history}

    Loads prior conversational context, prior execution artifact summaries,
    and dataset continuity constraints.

    \texttt{describe\_dataset}

    Loads and summarizes dataset schema only once per session for efficiency.

    \texttt{planner}

    Uses an LLM to:

    \begin{itemize}
        \item Determine if the query is a follow-up
        \item Decide whether visualization is useful
        \item
        Create:
        \begin{itemize}
            \item question
            \item data\_spec
            \item viz\_spec
        \end{itemize}
    \end{itemize}

    \vspace*{\fill}\columnbreak

    \texttt{codegen}

    Generates Python analysis code over the dataset.

    \texttt{execute}

    Runs generated code, stores structured execution artifacts, and summarizes result structure.

    \texttt{respond}

    Generates concise natural-language answers from execution results.

    \texttt{visualize\_codegen}

    Generates Plotly code if visualization is useful.

    \texttt{visualize\_execute}

    Executes Plotly code and returns frontend-compatible JSON.

    \vspace*{\fill}
\end{multicols}

\chap{Design}

\sect{Architectural Design Principles}

\begin{itemize}
    \item Modular
    \item Interpretable
    \item Debuggable
    \item Stateful
    \item Frontend/backend separated
\end{itemize}

\sect{Design Rationale}

Rather than forcing all downstream tasks to operate exclusively on reduced execution artifacts, the system preserves:


Execution \textbf{artifact} = reasoning state
\hfill
Original \textbf{dataset} = authoritative information state

This hybrid approach improved:

\begin{itemize}
    \item Visualization quality
    \item Follow-up flexibility
    \item Analytical correctness
\end{itemize}

\chap{Execution Result Design}
% ============================================================


\sect{Representation}

Each execution produces a structured artifact:

\begin{minted}{Python}
{
    "metadata": {
        "session_id": str,
        "run_id": str,
        "prompt": str,
        "dataset_name": str,
        "status": str,
    },
    "plan": {
        "is_follow_up": bool,
        "do_response": bool,
        "do_vis": bool,
        "question": str,
        "viz_spec": str,
        "data_spec": None,
    },
    "recent_context": None,
    "previous": {
        "data": {},
        "data_desc": str
    },
    "dataset_desc": str,
    "execution": {
        "data_code": str,
        "data": {},
        "data_desc": str,
        "error": str
    },
    "vis": {
        "vis_code": str,
        "fig": {},
        "error": str
    },
    "response": str,
}
\end{minted}

\sect{Why?}

The execution result is designed primarily as a debuggable interface between reasoning stages

\begin{multicols}{2}
    It stores:

    \begin{itemize}
        \item Generated code
        \item Computed structured outputs
        \item Summary statistics
        \item Errors
        \item Visualization state
    \end{itemize}

    \vspace*{\fill}\columnbreak

    This allows:

    \begin{itemize}
        \item Inspection
        \item Logging
        \item Session memory
        \item Follow-up context
    \end{itemize}

    \vspace*{\fill}
\end{multicols}

\begin{multicols}{2}
Through repeated testing, I found that reducing prior outputs into reusable artifacts often discarded critical dimensions necessary for:

\begin{itemize}
    \item Rich visualizations
    \item Complex filtering
    \item Aggregation changes
    \item Alternate chart types
    \item Flexible follow-up analysis
\end{itemize}

\vspace*{\fill}\columnbreak

For example: If a prior result stores only top-10 geographic regions by median housing price, a later request like: ``Now compare these by population density'' cannot be completed without missing source columns.

Thus, strict artifact-only reuse created:

\begin{itemize}
    \item Information bottlenecks
    \item Reduced generality
    \item Poor visualizations
\end{itemize}

\vspace*{\fill}
\end{multicols}

\sect{Trade-Offs}

\begin{multicols}{2}
    Advantages

    \begin{itemize}
        \item Higher correctness
        \item Better visualizations
        \item More flexible follow-up
        \item Avoids lossy intermediate states
        \item Cleaner debugging
        \item Simpler, smaller LLM calls
    \end{itemize}

    \vspace*{\fill}\columnbreak

    Disadvantages

    \begin{itemize}
        \item Less computational reuse
        \item Divergence from assignment ideal
    \end{itemize}

    \vspace*{\fill}
\end{multicols}

\sect{In/Out}

\begin{multicols}{2}
    The visualization agent receives:

    \begin{itemize}
        \item User question
        \item Planner-generated viz\_spec
        \item Dataset description
        \item Execution context
    \end{itemize}

    \vspace*{\fill}\columnbreak

    \begin{itemize}

        \item Executed Plotly figure JSON
        \item Error state
    \end{itemize}
    \vspace*{\fill}
\end{multicols}

\sect{Required Information for Visualization}

\begin{multicols}{2}
    The visualization system requires:

    \begin{itemize}
    \item Semantic chart goal
    \item Dataset schema
    \item Access to source-level granularity
    \end{itemize}

    \vspace*{\fill}\columnbreak

    Visualizations often require:

    \begin{itemize}
        \item Multiple columns
        \item Alternate grouping
        \item Temporal context
        \item Additional dimensions
    \end{itemize}
    \vspace*{\fill}
\end{multicols}

A reduced execution result almost always lacked enough structural richness.

\sect{Frontend Usage}

\begin{multicols}{2}
    Plotly JSON is sanitized and passed to the frontend, where:

    \begin{minted}{JavaScript}
        Plotly.newPlot(...)
    \end{minted}

    \vspace*{\fill}\columnbreak

    This allows:

    \begin{itemize}
        \item Interactive charts
        \item Dynamic rendering
        \item Session replay
    \end{itemize}
\end{multicols}

\chap{Failure Case}
% ============================================================


- At least one failure or limitation related to system behavior (e.g., reasoning, execution, memory, or visualization)
- What went wrong and why
- How the system could be improved


In an earlier iteration of the architecture, a consistent failure was in creating visualizations. I instructed the model to pass forward enough information to create visualizations from the data extraction node. However, this information was consistently hard to explain to the visualization code generated, as it was non-deterministically presented, despite my best efforts. Often, visualization would fail entirely due to this issue. Further, this created huge, expensive API calls.

A related failure case is as follows:

``Identify areas with similar median income levels but significantly different median house values. What factors might explain these differences?''

The data extraction node extracted so many points from the dataset, that the node responsible for generating responses was overwhelmed. It said:

\begin{minted}{md}
    Examples from the data (coordinates, median_income → median_house_value) and likely explanatory factors:

    - (-118.09,33.74) 4.6369 → 422,200 (NEAR OCEAN) vs (-121.37,38.63) 4.6127 → 151,800 (INLAND). Explanation: ocean_proximity (coastal premium) is the primary difference; housing ages (44 vs 30) and similar persons/household suggest location drives value gap.

    - (-122.49,37.50) 4.5625 → 500,000 (NEAR OCEAN) vs (-117.69,34.08) 4.5185 → 142,500 (INLAND). Explanation: near-ocean location correlates with much higher value despite similar incomes; housing size/age differences are secondary.

    - (-118.34,34.16) 3.6486 → 246,900 vs (-118.36,33.96) 3.6583 → 177,300 (both <1H OCEAN). Explanation: newer/larger housing and much lower population-per-household (1.59 vs 3.39) and total_rooms differences explain higher value within same proximity.
\end{minted}

To me, this indicated that it was not really able to identify factors leading to different median house values despite similar median income levels. This also might be because the prompt itself is vague. As noted in HW1, ``similar'' and ``significantly different'' are not very clear requirements.

However, possibly improvements could be made to the system. Shifting to a plan involving less output from the data extraction node would help the response node to generate coherent responses. This was a large part of the reasoning to shift towards referencing the whole dataset. Not doing so created a big data size/explanation issue that did not make sense in production.

\chap{Final Reflection}
% ============================================================


This project demonstrated that building an interactive dataset agent is fundamentally a systems design problem rather than only an LLM problem.

\sect{Key Lessons}

\begin{itemize}
    \item Clean modularity matters
    \item Memory is more than chat history
    \item Visualization requires richer context than text responses
    \item Over-compressing execution state can reduce system usefulness
\end{itemize}

\sect{Major Design Conclusion}

While assignment specifications emphasized artifact-only downstream reuse, practical testing revealed that preserving original dataset access significantly improved analytical flexibility and visualization quality.

Thus, I adopted a hybrid design that where prior results inform reasoning and the original dataset preserves capability.

\sect{Final Assessment}

This design prioritizes:

\begin{itemize}
    \item Correctness
    \item Robustness
    \item Generality
    \item Developer interpretability
\end{itemize}

Although this approach increases recomputation, it better supports real-world interactive data analysis.
